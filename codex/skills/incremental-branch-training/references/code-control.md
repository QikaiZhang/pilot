# 代码管控手册

用于路线 A/B、S/A/B 代码分级、代码生成边界和 Review 口径。

## 1. 路线 A/B 决策

每阶段开始前必须确认：

| 路线 | 适合人群 | AI 输出 | 学习者动作 |
| --- | --- | --- | --- |
| 路线A：留空手写 | 基础薄弱、第一次做项目 | 文件骨架、方法签名、注释、测试骨架、B级脚手架；S级函数体留空 | 填充 S级核心逻辑 |
| 路线B：删除重写 | 有基础、希望刻意训练独立编码 | 完整可运行参考代码；S级强标记 | 理解后删除 S级区域，从零重写 |

如果用户没有选择路线，不输出阶段代码。

## 2. S/A/B 分级细则

### S级：强制手写核心

判断标准：错了会影响系统核心正确性、数据一致性、安全性、并发稳定性，或面试一定会深挖。

常见 S级：

- 调度循环、任务抢占、优先级比较、时间轮、队列出入逻辑。
- 事务边界、扣库存、创建订单、支付回调、状态流转。
- 限流、熔断、重试、幂等、去重。
- 权限核心校验、签名验证、鉴权链路。
- 并发控制、锁、优雅关闭、资源回收。
- 分布式一致性、消息确认、补偿逻辑。

AI 允许提供：

- 设计解释。
- 伪代码。
- 函数签名。
- 单元测试。
- Review 和 bug 定位。

AI 不允许直接交付最终可复用 S级实现，除非路线B中明确标记删除重写。

### A级：AI 初稿，学习者重构

常见 A级：

- Entity、DTO、VO、枚举。
- Service/UseCase 骨架。
- Repository/DAO 基础结构。
- API 入参出参。
- 参数校验结构。

要求学习者：

- 改命名或补充字段设计理由。
- 补充必要注释。
- 能解释为什么放在这一层。
- 能说明哪些地方后续可能重构。

### B级：脚手架，读懂复用

常见 B级：

- 配置加载。
- 日志初始化。
- 路由注册。
- 基础测试模板。
- Dockerfile、Makefile、环境变量示例。
- 简单健康检查。

AI 可以直接生成，但仍要保持可读。

## 3. 代码输出格式

实现阶段先输出分级表：

```markdown
本阶段代码分级：
| 文件/模块 | 等级 | 原因 | AI 输出方式 |
| --- | --- | --- | --- |
|  | S/A/B |  |  |
```

路线A输出 S级代码时：

```go
func (s *Scheduler) PickNextTask() (*Task, error) {
    // TODO(S级): 请根据 Stage 设计，独立实现优先级选择逻辑。
    // 要求：
    // 1. 只选择状态为 pending 的任务
    // 2. 优先级高的先返回
    // 3. 同优先级按创建时间排序
    return nil, ErrNotImplemented
}
```

路线B输出 S级代码时：

```go
// WARNING S级核心逻辑：理解后必须删除本区域，并从零独立重写，禁止直接复用。
// 删除范围：从 BEGIN S_LEVEL_REFERENCE 到 END S_LEVEL_REFERENCE。
// BEGIN S_LEVEL_REFERENCE
func (s *Scheduler) PickNextTask() (*Task, error) {
    // reference implementation
}
// END S_LEVEL_REFERENCE
```

## 4. 可读性优先规则

主体实现偏向直观：

- 少用过度泛型、元编程、反射、复杂链式调用。
- 分支逻辑清楚展开，便于学习者断点调试。
- 错误处理显式，不吞异常。
- 关键边界使用测试覆盖，而不是只靠注释说明。

存在更优方案时，用优化提示：

```go
// 【优化提示】此处可以使用 xxx 方式简化实现或提升性能，适合后期迭代重构。
// 当前实现偏向直观易懂，优先保证可读性，便于理解数据流。
```

## 5. Review 口径

Review 学习者代码时，优先看：

1. S级是否真的由学习者完成，而不是保留 AI 参考实现。
2. 数据流是否符合阶段设计。
3. 边界场景是否遗漏。
4. 分层职责是否串层。
5. 命名是否能表达业务。
6. 测试是否覆盖关键路径。
7. 文档是否记录了设计取舍。

Review 输出格式：

```markdown
## Review 结果

必须修改：
1. 

建议优化：
1. 

已满足：
- 

验收结论：通过 / 不通过
```

## 6. 禁止行为

- 不要在路线A中补全 S级最终实现。
- 不要在未设计前生成库表、实体、核心流程。
- 不要把复杂业务逻辑全部塞进 Controller/Handler。
- 不要只生成代码，不更新阶段文档。
- 不要用“这里省略”跳过学习者需要理解的关键数据流。
- 不要为了显得高级而引入不必要框架或设计模式。
