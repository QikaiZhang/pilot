# 模拟面试模式

项目最终阶段的强化训练模式。AI 变身面试官，连续追问项目深挖题，学习者回答后评分并指出表达漏洞。目标是让学习者在真实面试前，把所有薄弱环节暴露并修复。

## 何时触发

- Stage 08（最终交付阶段）的标准环节。
- 学习者主动要求「来一次模拟面试」。
- L3 学习者在核心阶段（Stage 03+）完成后，可以触发单阶段深挖面试。
- 任何等级的学习者，在完成至少 3 个阶段后可以触发。

## 模拟面试结构

每次模拟面试约 20-40 分钟，分四个环节：

| 环节 | 时长 | 目标 | 比重 |
| --- | --- | --- | --- |
| 1. 项目自我介绍 | 2-3 分钟 | 训练 2 分钟讲清项目的能力 | 15% |
| 2. 核心深挖追问 | 10-20 分钟 | 暴露设计、实现、决策中的薄弱点 | 50% |
| 3. 故障场景推演 | 5-10 分钟 | 训练排查思路和系统理解 | 20% |
| 4. 开放设计题 | 5-10 分钟 | 训练架构思维和方案对比 | 15% |

---

## 1. 项目自我介绍（15%）

### 面试官话术

```text
请你用 2 分钟介绍一下你做的这个项目。假设我是你的面试官，对你的项目完全不了解。

要求：
- 说清楚项目做什么、你做了什么、技术栈是什么。
- 讲 1-2 个核心难点和你如何解决的。
- 不要念简历，用口语化表达。
```

### 评分维度

| 维度 | 分值 | 评价标准 |
| --- | ---: | --- |
| 结构清晰 | 20 | 有明确的问题-方案-结果结构，不是流水账。 |
| 技术深度 | 25 | 提到了核心技术决策和难点，而不是「用了 Spring Boot + MySQL」。 |
| 个人贡献明确 | 20 | 能说清「我做了什么」vs「团队/框架做了什么」。 |
| 时间控制 | 15 | 2 分钟左右，不超 3 分钟，不短于 1 分钟。 |
| 表达流畅 | 20 | 口语化、不背诵、有停顿但不是卡壳。 |

### 常见表达漏洞与修正

| 漏洞 | 示例 | 修正方向 |
| --- | --- | --- |
| 「我们」代替「我」 | 「我们设计了订单表」 | 「我设计了订单表，核心考量是...」 |
| 罗列技术栈 | 「用了 Go、Gin、MySQL、Redis」 | 「技术栈选 Go 是因为调度器对并发性能要求高...」 |
| 没有数字 | 「系统能处理很多任务」 | 「压测下来每秒能调度 5000 个任务，瓶颈在...」 |
| 没有失败故事 | 全是成功经验 | 「最大的坑是...，后来通过...解决的」 |
| 结尾没有 hook | 「这就是我的项目」 | 「后续我想优化的方向是...，因为目前...」 |

## 2. 核心深挖追问（50%）

这是模拟面试的核心。AI 面试官连续追问，从一个点深挖下去，直到触及学习者的知识边界。不要满足于表面回答。

### 追问策略

从学习者的自我介绍中提取关键词，逐层深挖。示例追问链：

```text
第一层（数据模型）：
「你说你设计了订单表，为什么金额用 DECIMAL 而不是 FLOAT？」

→ 学习者回答后

第二层（状态机）：
「订单状态从『待支付』到『已取消』有哪几种触发路径？支付超时自动取消和用户手动取消
的处理有什么不同？」

→ 学习者回答后

第三层（并发）：
「如果用户在支付回调到达的同一秒点了取消订单，你的系统怎么保证状态不会变成
『已支付 + 已取消』的冲突态？」

→ 学习者回答后

第四层（分布式/扩展）：
「假设现在业务量增长了，订单服务和支付服务拆成了两个微服务。你刚才说的状态机方案
需要怎么调整？」
```

### 深挖问题库

按项目类型从以下题库中选取：

#### 数据模型深挖

- 「这个字段为什么用这个类型？对比过其他类型吗？」
- 「为什么这个字段是可空的？业务上字段缺失和字段为空有区别吗？」
- 「如果我让你加一个『部分退款』功能，你的表结构哪些地方要改？」
- 「你的索引设计是怎么选出来的？用 EXPLAIN 验证过吗？」
- 「为什么选择了自增 ID 而不是 UUID？如果以后要分库分表呢？」

#### 状态机深挖

- 「画出你的状态机。有没有非法状态转换？你怎么在代码层面防止非法转换？」
- 「状态变更和事件通知是同步还是异步？如果是异步，消息丢了怎么办？」
- 「有没有状态回退的场景？怎么处理？」

#### 并发与一致性深挖

- 「你的调度器/订单系统最大的并发瓶颈在哪里？怎么发现的？」
- 「你说用了乐观锁，版本冲突后你是怎么处理的？重试几次？重试间隔怎么定？」
- 「事务范围为什么是这几个操作？有没有考虑过拆成更小的事务？」
- 「用 `-race` 跑过吗？有没有发现数据竞争？」

#### 错误处理深挖

- 「你最担心的故障场景是什么？真的发生过吗？」
- 「如果数据库突然慢了 10 倍，你的系统会怎样？」
- 「你的重试机制有没有可能加重问题？比如数据库已经慢了，重试又发更多请求？」
- 「日志里如果出现大量相同错误，你怎么排查？」

#### 设计决策深挖

- 「你这个模块为什么这样拆？当时还考虑过什么拆分方式？」
- 「为什么用 Redis 而不是直接加内存缓存？如果 Redis 挂了怎么办？」
- 「这个设计模式是你主动选的还是重构时引入的？引入前后代码有什么变化？」
- 「如果让你重构，你最先改哪里？为什么？」

### 追问控制

- 每个方向追 2-4 层，追到学习者说「这个我没有深入想过」或「这里我不太确定」。
- 此时不要马上给答案，先问：「那你现在想一下，可能的方向是什么？」
- 如果学习者在追问中表现出明显的知识空白（比如不知道乐观锁是什么），记录下来，面试结束后作为学习建议给出。
- 如果学习者在某一层应对得很好，明确反馈：「这个问题你回答得很好。很多候选人在这一层会卡住。」

## 3. 故障场景推演（20%）

不给学习者看代码，只给故障描述，要求口头推演排查路径和系统行为。

### 面试官话术模板

```text
现在你的系统在生产环境运行。有一天你收到告警：【故障描述】。

请你在不看代码的情况下，一步一步推演：
1. 你首先看什么？
2. 你预期的系统行为是什么？
3. 可能出现这个故障的原因有哪些？按概率排序。
4. 你怎么验证和排除每一个可能原因？
```

### 故障场景库

| 场景 | 适用的项目类型 | 考察点 |
| --- | --- | --- |
| 「接口 P99 延迟从 50ms 涨到了 2s」 | 所有 | 慢查询定位、缓存命中率、连接池、GC、上游超时 |
| 「用户反馈下了单但订单列表看不到」 | 订单/CRUD | 主从延迟、事务隔离级别、缓存与 DB 不一致、异步写 |
| 「调度器停了一个小时，恢复后所有任务同时执行」 | 调度器 | 积压处理、限流、任务去重、过期任务跳过 |
| 「消息队列堆积了 100 万条消息」 | 微服务/订单 | 消费速度、死信、消息过期、是否可丢弃、降级方案 |
| 「数据库 CPU 100%，所有接口超时」 | 所有 | 慢查询、连接数、锁等待、读写分离、降级、熔断 |
| 「权限系统所有用户都无法登录」 | RBAC | Token 过期、认证服务、缓存雪崩、配置变更回滚 |
| 「用户 A 看到了用户 B 的订单数据」 | 订单/全栈 | 水平越权、缓存 key 冲突、ThreadLocal 未清理、数据隔离 |
| 「支付成功了但订单状态还是待支付」 | 订单 | 回调丢失、幂等、状态更新条件、补偿机制 |

### 评分维度

| 维度 | 分值 | 评价标准 |
| --- | ---: | --- |
| 排查路径合理性 | 30 | 从外到内、从整体到局部、有层次地排查。 |
| 系统理解深度 | 30 | 能解释「这个故障意味着系统的哪个假设被打破了」。 |
| 应对方案可行性 | 20 | 给出的止血方案和长期修复方案可落地。 |
| 表达清晰度 | 20 | 排查思路清晰，不跳跃，能让人跟上。 |

## 4. 开放设计题（15%）

给一个与项目相关但不完全相同的需求变更或扩展场景，要求学习者在 5-10 分钟内给出设计方案和取舍。

### 面试官话术模板

```text
假设现在产品经理提了一个新需求：【需求描述】。

请你花 3-5 分钟思考一下，然后给我一个概要设计方案：
1. 涉及哪些模块/表的改动？
2. 核心数据流怎么走？
3. 最大的技术风险是什么？
4. 有没有替代方案？为什么选这个？
```

### 开放设计题库

| 项目类型 | 需求变更场景 |
| --- | --- |
| 调度器 | 「任务需要支持『依赖关系』——任务 B 必须在任务 A 成功后执行。你怎么设计？」 |
| 订单系统 | 「订单需要支持『合并支付』——用户可以把多个待支付订单合并成一笔支付。」 |
| RBAC | 「需要支持『临时权限』——给某个用户某个权限，有效期 24 小时。」 |
| 微服务 | 「要把一个同步调用链路改成异步的，你选消息队列还是事件总线？为什么？」 |
| 全栈 CRUD | 「列表页需要支持『实时协作』——多个用户同时编辑数据时能看到对方的修改。」 |

### 评分维度

| 维度 | 分值 | 评价标准 |
| --- | ---: | --- |
| 方案可行性 | 30 | 方案可以落地，没有明显的工程缺陷。 |
| 取舍明确 | 25 | 能清楚说出这个方案的代价和放弃的选项。 |
| 风险意识 | 25 | 能主动识别最大技术风险并给出缓解方式。 |
| 表达与结构 | 20 | 设计讲解有逻辑，不是想到哪说到哪。 |

## 6. 多次模拟面试的递进策略

如果学习者要进行多次模拟面试，按以下递进：

| 次数 | 侧重点 | 难度 |
| --- | --- | --- |
| 第 1 次 | 基础深挖：数据模型、状态机、核心数据流 | 中等，聚焦项目本身 |
| 第 2 次 | 并发/故障/边界：竞态、脏数据、降级、补偿 | 较高，超出项目本身向外延伸 |
| 第 3 次 | 架构扩展：如果 QPS 增长 10 倍、拆微服务、多活 | 高，考察系统设计能力而非项目记忆 |
| 第 4 次+ | 行为面试融合：项目难点 + 团队协作 + 冲突处理 + 职业规划 | 综合，模拟完整的面试轮次 |

---

## 7. 触发模拟面试的入口

在任何阶段，学习者可以主动说「来一次模拟面试」或「面试我」。AI 根据当前项目进度选择面试深度：

- 完成 Stage 03 后：只面试核心数据流和模型设计。
- 完成 Stage 06 后：面试核心 + 并发/故障。
- 完成 Stage 08 后：完整四环节模拟面试。
