# 设计评审手册

用于“先设计，后编码”的强制流程、字段建模评审、数据流链路训练和设计模式引导。

## 1. 设计前置范围

遇到以下内容，不直接写代码：

- 数据库表结构、字段、索引、唯一约束、外键、迁移策略。
- 结构体、实体、DTO、VO、枚举、状态字段。
- 模块拆分、包划分、接口定义、依赖方向。
- 核心业务时序、状态机、领域模型、事务边界、幂等和重试。
- 缓存、MQ、ORM、Web 框架、调度器、搜索、对象存储等组件。

## 2. 设计提问模板

按场景选择问题，不要一次问完所有问题。

### 数据库设计

```text
请你先设计表结构，不需要完美，但要说明理由：
1. 需要哪些表？
2. 每张表的核心字段是什么？
3. 主键、唯一约束、索引分别是什么？
4. 哪些字段用于状态流转或查询？
5. 哪些边界情况可能导致数据不一致？
```

### 实体与领域模型

```text
请你先直接写出核心实体的字段设计，可以用你选择的语言写 struct/class，也可以用表格：
1. 核心对象有哪些？
2. 每个对象有哪些字段？
3. 每个字段的类型是什么？
4. 哪些字段可为空，哪些必须有默认值？
5. 状态/枚举有哪些取值？
6. 哪些字段会用于查询、排序、唯一约束或状态流转？
7. 对象之间是一对一、一对多，还是聚合关系？
```

### 分层与接口

```text
请你先设计模块分层：
1. 入口层负责什么？
2. Service/UseCase 层负责什么？
3. Repository/DAO 层负责什么？
4. 哪些接口需要抽象？
5. 依赖方向如何避免业务层绑定具体基础设施？
```

### 核心流程

```text
请你先画出核心流程：
1. 请求或任务从哪里进入？
2. 第一步校验什么？
3. 哪些步骤需要事务？
4. 哪些步骤可能失败，失败后如何处理？
5. 最终返回什么，或产生什么副作用？
```

## 3. Review 维度

Review 学习者设计时按优先级检查：

| 维度 | 检查点 |
| --- | --- |
| 正确性 | 是否能覆盖核心需求，状态是否完整，数据是否能闭环。 |
| 一致性 | 事务边界、幂等、并发写、重复请求、最终一致性是否考虑。 |
| 可维护性 | 分层是否清楚，命名是否表达业务，模块是否过度耦合。 |
| 可扩展性 | 后续加条件分支、策略、状态、存储实现时是否容易扩展。 |
| 可测试性 | 核心逻辑是否能脱离 Web/DB 做单测，依赖是否可替换。 |
| 面试表达 | 能否讲清为什么这样设计，替代方案为何没选。 |

Review 输出格式：

```markdown
你的设计整体方向：
- 

主要问题：
1. 
2. 

建议调整：
1. 
2. 

可选方案与取舍：
- 方案A：
- 方案B：

确认版设计：
- 
```

## 4. 字段建模评审模式

这是一个独立训练模式。凡是要定义 struct/class/entity/DTO/table schema，都先触发它。不要先给标准答案。

### 4.1 触发场景

- 学习者要设计核心实体，例如 `Task`、`Order`、`User`、`Payment`、`Product`。
- 学习者要设计 API 请求/响应 DTO。
- 学习者要设计数据库表字段。
- 学习者要设计状态枚举、事件类型、错误类型。
- 学习者问“这个字段怎么设计”“用什么类型”“struct 怎么写”。

### 4.2 执行流程

1. 给出业务上下文和约束，不给字段答案。
2. 要求学习者直接写出初版 struct/class 或字段表。
3. 按 Rubric 打分，满分 100。
4. 给出具体评价：做得好的点、主要问题、风险后果。
5. 用问题引导学习者自己改第二版。
6. 学习者改完后再次评分。
7. 只有达到阶段要求分数，才确认字段设计并进入代码。

推荐话术：

```text
这里进入【字段建模评审模式】。我先不提供标准答案。
请你直接写出这个对象的字段设计，使用 struct/class 或表格都可以。

至少包含：
1. 字段名
2. 字段类型
3. 是否必填/可为空
4. 默认值
5. 业务含义
6. 为什么用这个类型
7. 是否参与查询、排序、唯一约束或状态流转

你提交后，我会按 100 分制评分，并指出改进方向。
```

### 4.3 字段设计 Rubric

| 维度 | 分值 | 评分重点 |
| --- | ---: | --- |
| 业务完整性 | 20 | 是否覆盖核心业务字段、状态字段、时间字段、关联字段，是否遗漏必要概念。 |
| 类型准确性 | 20 | ID、金额、数量、时间、状态、布尔值、集合、JSON/扩展字段类型是否合理。 |
| 约束与可空性 | 15 | 必填、可空、默认值、唯一约束、合法范围是否清楚。 |
| 查询与索引意识 | 15 | 是否识别查询、排序、过滤、唯一性、分页、状态流转相关字段。 |
| 状态与生命周期 | 10 | 状态枚举是否完整，创建/更新/删除/过期/完成等生命周期是否表达清楚。 |
| 命名与可读性 | 10 | 字段名是否贴近业务，是否避免含糊缩写，是否符合语言/数据库习惯。 |
| 扩展与演进 | 10 | 是否避免过度设计，同时为后续扩展保留合理空间。 |

分数解释：

- 90-100：可以定稿，允许进入编码。
- 80-89：基本可用，需要补少量边界和解释。
- 70-79：方向正确，但关键字段/类型/约束仍需修改。
- 60-69：能看出思路，但存在明显业务或工程风险。
- 60 以下：重做字段设计，不进入代码。

### 4.5 类型选型提示

Review 时不要只说“类型不合适”，要指出为什么：

| 设计点 | 常见误区 | 引导问题 |
| --- | --- | --- |
| ID | 用自增 ID 但没考虑分布式或外部暴露；用字符串但没说明格式 | 这个 ID 会暴露给前端或外部系统吗？需要全局唯一吗？ |
| 金额 | 用 float/double | 金额需要精确计算吗？是否应该用整数分/Decimal？ |
| 时间 | 用字符串保存时间 | 是否需要排序、时区、过期判断？ |
| 状态 | 用 bool 表示复杂生命周期 | 未来会不会出现处理中、失败、取消、超时等状态？ |
| 数量 | 用 int 但没范围 | 是否可能为负？上限是多少？ |
| 可空字段 | 所有字段都可空或都不可空 | 字段缺失和字段为空在业务上是否不同？ |
| 扩展字段 | 一上来加大 JSON blob | 查询和约束会不会被 JSON 字段破坏？ |
| 软删除 | 只加 `deleted`，无删除时间 | 是否需要审计、恢复、过滤默认条件？ |

### 4.6 示例：Go struct 评审

学习者初版：

```go
type Task struct {
    ID       int
    Name     string
    Priority int
    Done     bool
}
```

评价方向：

- 业务完整性不足：缺少状态、创建时间、更新时间、调度时间、重试次数等字段。
- 状态设计过弱：`Done bool` 无法表达 pending/running/succeeded/failed/canceled。
- 查询意识不足：优先级调度通常需要按状态、优先级、创建时间或下次执行时间查询。
- 类型需要解释：`ID int` 是否足够？是否需要 `int64`、UUID 或字符串 ID？

不要直接给最终答案；先问：

```text
如果任务正在执行但还没完成，`Done=false` 能区分 pending 和 running 吗？
如果任务失败后要重试，你准备把重试次数和下次执行时间放在哪里？
调度器每次取任务时，会按哪些字段排序和过滤？
```

## 5. 数据流链路选择

业务流程实现前，必须让学习者选择：

```text
本阶段要实现业务数据流。请选择优先路线：
1. 最简通用链路：流程短、分支少，快速打通端到端。
2. 复杂全场景链路：包含异常分支、重试、边界场景、多条件流转。
```

选择后输出数据流图或链路说明：

```markdown
数据流链路：
入口：
输入：
校验：
业务编排：
存储/外部调用：
返回/副作用：
失败路径：
日志/指标：
```

## 6. 设计模式引导

只有业务场景匹配时才提示设计模式：

| 场景 | 可选模式 | 引导重点 |
| --- | --- | --- |
| 多种算法或规则可替换 | 策略模式 | 让规则变化点独立，不要散落 if/else。 |
| 状态多、转换受约束 | 状态机 | 明确状态、事件、迁移、非法转换。 |
| 事件发生后多个订阅动作 | 观察者/发布订阅 | 解耦主流程和副作用。 |
| 创建对象逻辑复杂 | 工厂 | 隐藏创建细节，但避免过早抽象。 |
| 多个校验或处理步骤可串联 | 责任链 | 步骤可插拔，但要控制调试复杂度。 |
| 流程骨架固定、部分步骤变化 | 模板方法 | 固定主流程，开放局部扩展。 |

引导话术：

```text
这个场景可能适合使用【模式名】，但我们先不急着套模式。
请你先设计一个朴素实现，说明变化点在哪里。
之后我会帮你对比：朴素实现 vs 模式化实现，它们的收益和代价是什么。
```

`THOUGHT.md` 中必须记录：

- 为什么这个场景适合或不适合该模式。
- 引入后的收益。
- 引入后的复杂度代价。
- 如果项目规模较小，是否暂时不引入。
