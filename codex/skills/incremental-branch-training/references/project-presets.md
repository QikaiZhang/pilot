# 项目类型预设包

给不同项目类型提供定制的训练路线、阶段拆解、技术栈建议和常见坑位。选择一个预设作为起点，然后根据学习者水平和目标岗位调整。

## 如何使用预设

在新项目启动时，按以下步骤：

1. 根据学习者的项目方向匹配最接近的预设。
2. 把预设的阶段拆分展示给学习者，确认或调整。
3. 用预设中的「关键训练点」决定每个阶段的 S/A/B 分级重点。
4. 用预设中的「常见坑位」在设计 Review 时主动提问。

预设不是死板的——如果学习者的项目横跨多个类型（比如「带权限的订单系统」），合并相关预设的阶段。

## 预设 1：并发调度器训练路线

适合岗位方向：Go/C++/Java 后端，偏基础架构、中间件、云原生。

### 技术栈建议

| 选项 | 推荐组合 |
| --- | --- |
| 入门 | Go + `container/heap` + `sync.Mutex` + `context` |
| 进阶 | Go + `ants` 协程池 + `sync.WaitGroup` + channel |
| 分布式方向 | Go/Java + Redis/ZooKeeper + Kafka + gRPC |

### 定制阶段拆分（7 阶段）

| 阶段 | 目标 | 关键训练点 | 分支 |
| --- | --- | --- | --- |
| Stage 01 | 调度器核心模型设计 | Task 字段建模、优先级策略、状态生命周期 | `stage/01-scheduler-model` |
| Stage 02 | 工程骨架与任务队列 | 分层结构、内存队列、配置加载 | `stage/02-scheduler-skeleton` |
| Stage 03 | 核心调度循环（S级） | 优先级比较、任务出队、并发拉取、优雅关闭 | `stage/03-scheduler-loop` |
| Stage 04 | 错误与超时处理 | 任务超时、失败重试、panic 恢复、context 取消 | `stage/04-error-handling` |
| Stage 05 | 任务持久化 | 内存+DB 双写、重启恢复、幂等去重 | `stage/05-persistence` |
| Stage 06 | 高级调度策略 | 时间轮、延迟队列、优先级继承、公平调度 | `stage/06-advanced-strategy` |
| Stage 07 | 测试与面试交付 | 并发测试、数据竞争检测、系统设计文档、口述 | `stage/07-test-deliver` |

### 每阶段 S级标注

| 阶段 | S级内容 |
| --- | --- |
| Stage 01 | Task 字段设计（必须手写，AI Review 打分） |
| Stage 02 | 无 S级，主要是 A/B 级脚手架 |
| Stage 03 | `PickNextTask()`、`ExecuteTask()`、`Run()` 调度主循环、`Shutdown()` 优雅关闭 |
| Stage 04 | 超时处理逻辑、重试策略判断、panic recover 包装 |
| Stage 05 | 写 DB 的事务边界、重启恢复的状态重建逻辑 |
| Stage 06 | 时间轮 advance、延迟队列 push/pop、优先级继承算法 |
| Stage 07 | 并发竞态测试用例、`-race` 数据竞争修复 |

### 关键训练点

- **并发安全**：每个共享数据结构必须能解释为什么安全（锁粒度、channel 替代锁、无锁结构）。
- **优雅关闭**：能画出 shutdown 信号传播路径：`ctx.Done()` → 停止接收新任务 → 等待进行中任务 → 释放资源。
- **数据结构选型**：heap vs 红黑树 vs 时间轮，能讲清各自适用的调度场景。
- **面试深挖**：「你的调度器如何处理任务堆积？」「优先级反转怎么解决？」

### 常见坑位

- `Done bool` 替代状态枚举，无法区分 pending/running/succeeded/failed。
- 锁粒度过大导致调度吞吐下降。
- channel 关闭后继续写入导致 panic。
- 没有区分「任务超时」和「调度器关闭」两种取消场景。
- 优先级只用 int 比较，没考虑同优先级的时间顺序（FIFO）。

## 预设 2：订单系统训练路线

适合岗位方向：Java/Go/Python 后端，偏业务开发、电商、交易系统。

### 技术栈建议

| 选项 | 推荐组合 |
| --- | --- |
| 入门 | Java + Spring Boot + MyBatis + MySQL |
| Go 方向 | Go + Gin/chi + sqlx/GORM + PostgreSQL |
| Python 方向 | Python + FastAPI + SQLAlchemy + PostgreSQL |

### 定制阶段拆分（8 阶段）

| 阶段 | 目标 | 关键训练点 | 分支 |
| --- | --- | --- | --- |
| Stage 01 | 需求澄清与领域建模 | 订单、商品、用户实体关系、状态机初版 | `stage/01-order-model` |
| Stage 02 | 工程骨架与分层 | Controller/Service/Repository、统一返回格式 | `stage/02-order-skeleton` |
| Stage 03 | 下单核心闭环（S级） | 库存扣减、订单创建、事务边界、幂等 | `stage/03-place-order` |
| Stage 04 | 订单状态流转 | 支付回调、发货、完成、取消、退款状态机 | `stage/04-order-status` |
| Stage 05 | 查询与列表 | 分页、多条件筛选、索引设计、慢查询优化 | `stage/05-order-query` |
| Stage 06 | 异常与并发 | 超卖、重复下单、分布式锁、消息去重 | `stage/06-concurrency` |
| Stage 07 | 测试与重构 | 事务测试、状态机测试、Mock 支付回调 | `stage/07-order-test` |
| Stage 08 | 面试交付 | 系统设计文档、订单面试问答手册、口述 | `stage/08-order-deliver` |

### 每阶段 S级标注

| 阶段 | S级内容 |
| --- | --- |
| Stage 01 | 订单/订单项/商品/用户字段设计、状态枚举设计、金额类型选型 |
| Stage 02 | 无 S级，分层结构由 AI 提供骨架 |
| Stage 03 | 库存扣减逻辑、订单创建事务、幂等键设计 |
| Stage 04 | 状态迁移函数、无效迁移拒绝逻辑、事件发布 |
| Stage 05 | 无 S级，主要是索引设计（算设计阶段 S级） |
| Stage 06 | 超卖防护逻辑、分布式锁获取与释放、消息去重判断 |
| Stage 07 | 事务回滚测试、并发下单压力测试 |
| Stage 08 | 系统设计文档全部手写（AI Review） |

### 关键训练点

- **事务边界**：能画出下单的事务范围——哪些操作必须在一个事务里，哪些必须在外围。能解释「先扣库存再创建订单」和「先创建订单再扣库存」的差异。
- **状态机**：状态 × 事件 → 新状态 的完整矩阵。能讲清「支付回调到达时订单还在创建中」怎么处理。
- **金额精度**：能用整数分/Decimal，能解释为什么不能用 float/double。
- **幂等**：能区分「前端防重」、「接口幂等」、「消息去重」三个层面的差异。
- **面试深挖**：「如果下单成功但支付回调丢失怎么办？」「库存扣减和订单创建不在同一个数据库怎么办？」

### 常见坑位

- 金额用 `float64`/`double`。
- 订单状态用多个 bool 字段拼凑。
- 没区分「下单超时」和「库存不足」的错误码和错误信息。
- 索引只在单字段上加，没考虑联合索引的列顺序。
- 乐观锁版本号没放在 UPDATE 的 WHERE 里。

## 预设 3：用户权限系统（RBAC）训练路线

适合岗位方向：后端开发，偏企业级系统、SaaS、安全方向。

### 技术栈建议

| 选项 | 推荐组合 |
| --- | --- |
| 入门 | Java + Spring Boot + Spring Security + MyBatis + MySQL |
| Go 方向 | Go + Gin + Casbin/jwt + sqlx + PostgreSQL |
| Python 方向 | Python + FastAPI + FastAPI-users + SQLAlchemy + PostgreSQL |

### 定制阶段拆分（7 阶段）

| 阶段 | 目标 | 关键训练点 | 分支 |
| --- | --- | --- | --- |
| Stage 01 | 权限模型设计 | 用户-角色-权限模型、资源定义、字段建模 | `stage/01-rbac-model` |
| Stage 02 | 工程骨架与认证 | 登录、JWT/Token、密码加密、中间件 | `stage/02-auth-skeleton` |
| Stage 03 | RBAC 核心鉴权（S级） | 权限校验链路、角色继承、资源匹配 | `stage/03-rbac-core` |
| Stage 04 | 权限管理接口 | 角色 CRUD、权限分配、用户-角色绑定 | `stage/04-permission-api` |
| Stage 05 | 数据权限 | 行级权限、部门隔离、租户隔离 | `stage/05-data-permission` |
| Stage 06 | 安全加固 | 暴力破解防护、Token 刷新/吊销、审计日志 | `stage/06-security` |
| Stage 07 | 测试与面试交付 | 权限矩阵测试、越权测试、设计文档 | `stage/07-permission-deliver` |

### 每阶段 S级标注

| 阶段 | S级内容 |
| --- | --- |
| Stage 01 | 用户/角色/权限/资源字段设计、角色继承关系设计 |
| Stage 02 | 无 S级，认证流程由 AI 提供骨架 |
| Stage 03 | 权限匹配算法（通配符/层级/优先级）、鉴权决策函数 |
| Stage 04 | 权限变更的原子性、角色删除时的级联处理 |
| Stage 05 | 行级权限过滤逻辑、租户上下文注入 |
| Stage 06 | Token 吊销策略、审计日志写入 |
| Stage 07 | 越权测试用例设计（水平越权、垂直越权） |

### 关键训练点

- **模型设计**：RBAC vs ABAC vs ReBAC，能讲清什么时候用哪种。
- **鉴权链路**：能画出一个请求从到达 → 认证 → 鉴权 → 业务处理 → 返回的完整链路。
- **数据权限**：能区分「功能权限」和「数据权限」，能设计行级过滤方案。
- **安全思维**：能识别越权风险点，能设计审计日志记录策略。
- **面试深挖**：「如果一个用户既是部门管理员又是普通员工，权限怎么合并？」「权限变更后已在线的 Token 怎么处理？」

### 常见坑位

- 权限判断散落各处（Controller 层、Service 层、SQL 层），没有统一鉴权点。
- 角色和权限混淆——把「管理员」当成权限名而不是角色名。
- 忘记设计资源（Resource）和操作（Action）的抽象层。
- Token 永不过期，没有刷新和吊销机制。
- 密码明文存储或使用弱哈希。

## 预设 4：微服务项目训练路线

适合岗位方向：后端/全栈开发，偏分布式系统、架构方向（中高级）。

### 技术栈建议

| 选项 | 推荐组合 |
| --- | --- |
| Go 方向 | Go + gRPC + protobuf + Kafka/NATS + Consul/etcd |
| Java 方向 | Java + Spring Cloud + RabbitMQ + Nacos + Sentinel |
| 通用 | Docker + Docker Compose + PostgreSQL + Redis |

### 定制阶段拆分（8 阶段 + 可选扩展）

| 阶段 | 目标 | 关键训练点 | 分支 |
| --- | --- | --- | --- |
| Stage 01 | 服务拆分设计 | 限界上下文、服务边界、API 契约、数据归属 | `stage/01-service-boundary` |
| Stage 02 | 工程骨架（单服务） | 先做一个服务的完整分层、再复制到其他服务 | `stage/02-service-skeleton` |
| Stage 03 | 服务间同步调用 | gRPC/HTTP 调用、proto/OpenAPI 定义、序列化 | `stage/03-sync-call` |
| Stage 04 | 异步消息（S级） | 消息生产/消费、顺序、去重、死信、补偿 | `stage/04-async-msg` |
| Stage 05 | 分布式事务 | Saga/TCC/Outbox、补偿逻辑、最终一致性 | `stage/05-dist-tx` |
| Stage 06 | 服务治理 | 服务发现、负载均衡、熔断、限流、重试 | `stage/06-governance` |
| Stage 07 | 可观测性 | 日志聚合、链路追踪、指标暴露、告警 | `stage/07-observability` |
| Stage 08 | 测试与面试交付 | 集成测试、混沌测试、系统设计文档 | `stage/08-ms-deliver` |

### 每阶段 S级标注

| 阶段 | S级内容 |
| --- | --- |
| Stage 01 | 服务边界图、API 契约字段设计、数据所有权判断 |
| Stage 02 | 无 S级 |
| Stage 03 | 无 S级（主要是集成和配置，算 A级） |
| Stage 04 | 消息 handler 核心处理逻辑、幂等判断、死信处理、补偿逻辑 |
| Stage 05 | Saga 编排/协调逻辑、补偿操作、Outbox 发布 |
| Stage 06 | 熔断判断、限流算法实现（令牌桶/滑动窗口） |
| Stage 07 | 无 S级（主要是集成，算 A级） |
| Stage 08 | 端到端数据流讲解、系统设计文档 |

### 关键训练点

- **服务边界**：能画出服务间的数据依赖图。能讲清为什么某个数据属于服务 A 而不是服务 B。
- **异步消息**：能讲清「消息丢了」、「消息重复了」、「消息乱序了」三种故障场景的处理。
- **分布式事务**：能对比 2PC、Saga、TCC、Outbox 的适用场景和代价。
- **面试深挖**：「如果下游服务挂了，消息堆积怎么处理？」「分布式事务的回滚失败了怎么办？」

### 常见坑位

- 服务拆得太碎，一个 CRUD 功能跨 3 个服务。
- 把同步调用和异步消息混用，没有明确的数据一致性边界。
- 消息没有唯一 ID，消费端无法去重。
- Saga 补偿逻辑没有测试过失败路径。
- 微服务先上全套治理组件（Istio、Consul、链路追踪），而不是先打通核心业务流。

### 前置条件

此预设要求学习者已经完成过一个单体项目的训练（推荐先完成预设 1 或 2）。不适合零基础或首次做项目。

## 预设 5：全栈 CRUD 产品训练路线

适合岗位方向：全栈开发、前端偏后端、个人作品集。

### 技术栈建议

| 选项 | 推荐组合 |
| --- | --- |
| TypeScript 全栈 | Next.js + Prisma + PostgreSQL + tRPC/Zod |
| React + Go | React + Vite + Go/Gin + sqlx + PostgreSQL |
| Vue + Java | Vue 3 + Vite + Spring Boot + MyBatis + MySQL |

### 定制阶段拆分（8 阶段）

| 阶段 | 目标 | 关键训练点 | 分支 |
| --- | --- | --- | --- |
| Stage 01 | 产品范围与数据模型 | 用户故事、页面清单、实体关系、字段建模 | `stage/01-product-model` |
| Stage 02 | 后端骨架与首条 API | 分层、第一个 CRUD 端点、参数校验 | `stage/02-backend-skeleton` |
| Stage 03 | 核心业务 CRUD（S级） | 创建/编辑时的业务校验、关联数据处理 | `stage/03-core-crud` |
| Stage 04 | 前端骨架与首屏 | 路由、组件树、API 调用封装、状态管理 | `stage/04-frontend-skeleton` |
| Stage 05 | 前后端联调全链路 | 完整数据流打通、错误展示、Loading 状态 | `stage/05-full-link` |
| Stage 06 | 用户系统 | 注册/登录/鉴权、个人中心、权限控制 | `stage/06-user-system` |
| Stage 07 | 体验与边界 | 表单校验、乐观更新、分页加载、搜索 | `stage/07-ux-boundary` |
| Stage 08 | 部署与面试交付 | Docker 部署、CI/CD 基础、作品集文档 | `stage/08-deploy-deliver` |

### 每阶段 S级标注

| 阶段 | S级内容 |
| --- | --- |
| Stage 01 | 实体字段设计、API 契约设计（请求/响应 DTO） |
| Stage 02 | 无 S级，分层骨架由 AI 提供 |
| Stage 03 | 创建/编辑时的业务校验逻辑、关联数据一致性处理 |
| Stage 04 | 无 S级，组件骨架由 AI 提供 |
| Stage 05 | 错误处理策略、请求/响应类型对齐（手写纠错） |
| Stage 06 | 密码哈希、Token 管理、权限中间件 |
| Stage 07 | 无 S级，主要是 A/B 级实现 |
| Stage 08 | 系统设计文档、面试口述 |

### 关键训练点

- **前后端契约**：能先定义 API 请求/响应类型，再分别写前后端代码，而不是边写边改。
- **数据流全链路**：能从前端表单提交讲到后端写库再到前端刷新列表。
- **错误处理**：能区分「网络错误」、「业务错误」、「校验错误」在前端的展示方式。
- **面试深挖**：「你的应用怎么处理用户点了两次提交按钮？」「列表数据量大后怎么优化？」

### 常见坑位

- 前后端类型不一致，前端用 camelCase，后端用 snake_case，靠运行时隐式转换。
- 接口设计按页面 UI 来，而不是按资源和业务操作来。
- 所有状态全放 React Context/Redux，没有区分服务端状态和客户端状态。
- 创建和编辑用同一套校验，但实际上创建时某些字段必填、编辑时可空。
- 没有 Loading/Empty/Error 三态的完整覆盖。

## 预设的组合使用

实际项目中，一个产品可能横跨多个预设。例如：

**「带权限管理后台的订单系统」** = 预设 2（订单系统）+ 预设 3（RBAC）+ 预设 5（前端）

合并策略：取最核心的业务预设作为主线（比如订单系统），把其他预设中相关的阶段插入合适位置。

合并示例：

| 阶段 | 来源 | 内容 |
| --- | --- | --- |
| 01 | 预设 2 | 订单领域建模 |
| 02 | 预设 2 | 订单骨架 |
| 03 | 预设 3 | RBAC 模型设计 |
| 04 | 预设 2 | 下单核心闭环 |
| 05 | 预设 3 | 鉴权中间件集成 |
| 06 | 预设 5 | 前端骨架 |
| 07 | 预设 5 | 前后端联调 |
| 08 | 预设 3 | 数据权限 |
| 09 | 交付 | 设计文档、面试问答 |

不要把所有预设的阶段全叠加上去——单个训练项目的阶段不宜超过 10 个。
