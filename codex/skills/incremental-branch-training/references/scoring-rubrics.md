# 评分体系：从字段到系统的量化训练反馈

这份文件把训练中每个关键环节都配上 100 分制 Rubric，让学习者在每个阶段都能看到量化的成长轨迹，而不仅仅是「通过/不通过」。

## 评分体系总览

| 评分环节 | 触发时机 | 主要文件 | 入门门槛 |
| --- | --- | --- | --- |
| 字段建模评分 | 设计 struct/class/table/DTO 字段时 | 本文第 1 节 | ≥ 80 分进入编码 |
| 设计 Review 评分 | Stage 01 整体设计定稿时 | 本文第 2 节 | ≥ 75 分进入实现 |
| 数据流讲解评分 | 每阶段数据流链路讲完后 | 本文第 3 节 | ≥ 80 分通过口述验收 |
| S级代码质量评分 | S级函数提交 Review 时 | 本文第 4 节 | ≥ 80 分通过代码验收 |
| 阶段综合评分 | 每阶段验收时 | 本文第 5 节 | ≥ 80 分进入下一阶段 |
| 模拟面试评分 | 最终阶段或单独触发时 | 本文第 6 节 | 各维度独立评分 |

## 1. 字段建模评分（100 分）

与 `design-review.md` 第 4.3 节一致，此处为完整版。

| 维度 | 分值 | 评分重点 | 扣分信号 |
| --- | ---: | --- | --- |
| 业务完整性 | 20 | 核心业务字段、状态字段、时间字段、关联字段是否覆盖。是否遗漏必要概念。 | 缺状态字段；缺少时间维度（创建/更新）；缺少关联键 |
| 类型准确性 | 20 | ID、金额、数量、时间、状态、布尔值、集合、JSON/扩展字段类型是否合理。 | 金额用 float/double；时间用字符串；ID 不考虑分布式；bool 表示复杂状态 |
| 约束与可空性 | 15 | 必填、可空、默认值、唯一约束、合法范围是否清楚。 | 全部可空或全部不可空无说明；金额无范围；字符串无长度限制 |
| 查询与索引意识 | 15 | 是否识别查询、排序、过滤、唯一性、分页、状态流转相关字段。 | 未标注任何查询/索引用途；联合索引无列顺序说明 |
| 状态与生命周期 | 10 | 状态枚举完整性，生命周期表达是否清楚。 | 用 bool 拼凑状态；遗漏取消/超时/失败等关键状态；状态迁移路径不清 |
| 命名与可读性 | 10 | 是否贴近业务，避免含糊缩写，符合语言/数据库习惯。 | 拼音命名；无意义缩写（`st`/`dt`）；数据库用 camelCase 而非 snake_case |
| 扩展与演进 | 10 | 是否避免过度设计，同时为扩展留合理空间。 | 过度设计（一上来 30 个字段全未来需求）；零扩展空间（后续要加状态就得改类型） |

**分数解释**：

| 分数 | 结论 | 后续动作 |
| ---: | --- | --- |
| 90-100 | 可以定稿 | 直接进入编码，只需在 THOUGHT.md 记录最终设计 |
| 80-89 | 基本可用 | 补少量边界说明后进入编码 |
| 70-79 | 方向正确 | 修改关键字段/类型/约束，提交第二版 |
| 60-69 | 存在风险 | 有明显业务或工程风险，需要较大修改 |
| < 60 | 不通过 | 重新做字段设计，AI 可以给设计方向提示但不给字段答案 |

## 2. 设计 Review 评分（100 分）

用于 Stage 01 整体设计定稿时的综合评审。与字段建模评分互补——字段建模聚焦字段层面，设计 Review 聚焦架构层面。

| 维度 | 分值 | 评分重点 | 扣分信号 |
| --- | ---: | --- | --- |
| 需求覆盖度 | 20 | 设计是否覆盖了本阶段所有需求点。是否理解业务边界。 | 漏掉核心用例；非功能性需求完全没有考虑（如并发、安全） |
| 分层与模块划分 | 20 | 分层职责是否清晰，模块边界是否合理，依赖方向是否正确。 | 业务逻辑全在 Controller/Handler；循环依赖；模块按技术层而不是业务拆分 |
| 接口与契约设计 | 15 | API 入参出参是否完整，错误码是否有层次，接口是否向后兼容。 | 所有错误返回 500；没有版本意识；入参不加校验约束 |
| 数据一致性 | 15 | 事务边界、幂等、并发写、最终一致性是否有基本考虑。 | 跨表操作无事务；无幂等意识；乐观锁/悲观锁策略缺失 |
| 可测试性 | 10 | 核心逻辑是否能脱离 Web/DB 做单测，依赖是否可替换。 | 全部逻辑绑定具体框架；数据库直接写在业务层；无接口抽象 |
| 可扩展性 | 10 | 后续加条件分支、策略、状态、存储实现时是否容易扩展。 | 硬编码 if/else 无策略模式意识；状态变更要改所有相关代码 |
| 安全与边界 | 10 | 是否有基本的输入校验、越权防护、敏感信息保护意识。 | 无输入校验；无鉴权设计；敏感字段无脱敏意识 |

**分数解释**：

| 分数 | 结论 | 后续动作 |
| ---: | --- | --- |
| 90-100 | 定稿 | 设计的架构层面已经没有明显缺陷，进入路线选择和代码分级 |
| 75-89 | 基本可用 | 有 1-2 个维度需要补充说明，修改后可进入编码 |
| 60-74 | 存在风险 | 架构层面有 2 个以上维度需要较大调整 |
| < 60 | 不通过 | 重新设计，AI 可以给架构层面的引导问题 |

## 3. 数据流讲解评分（100 分）

用于每阶段数据流链路讲完后的口述验收。这个评分直接对应面试中「讲清你的数据流」的能力。

| 维度 | 分值 | 评分重点 | 扣分信号 |
| --- | ---: | --- | --- |
| 入口清晰 | 15 | 是否讲清请求/事件从哪里进入、携带什么数据、入口做了哪些通用处理（认证、限流、格式校验）。 | 「从前端发请求过来」——太笼统；没说参数校验在入口做还是业务层做 |
| 校验链路 | 15 | 是否讲清每层校验的职责：入口校验什么、业务层校验什么、存储前校验什么。 | 把校验全堆在一个地方；没说校验失败后返回什么 |
| 业务编排 | 20 | 是否讲清核心业务步骤、调用顺序、分支条件、事务范围。 | 跳过关键判断逻辑；没说「为什么先做 A 再做 B」；事务边界模糊 |
| 存储与外部调用 | 15 | 是否讲清读写哪些表/外部服务、顺序、失败后对上游的影响。 | 只说「存数据库」而不说存哪些表；没说存储失败怎么处理 |
| 返回与副作用 | 15 | 是否讲清返回值、事件发布、日志、指标、缓存失效等副作用。 | 忽略异步事件发布；没提日志/指标；没说返回结构 |
| 失败路径 | 20 | 是否讲清每个环节可能的失败、如何传播、如何降级、如何补偿。 | 所有失败统一「返回错误」——没有区分超时/业务失败/系统故障/可重试/不可重试 |

**分数解释**：

| 分数 | 结论 | 后续动作 |
| ---: | --- | --- |
| 90-100 | 链路清晰 | 数据流讲解达到面试水平，可以自信地回答「核心数据流是什么」 |
| 80-89 | 基本清楚 | 主干链路讲清了，失败路径有 1-2 处模糊，补充后可进入编码 |
| 70-79 | 有缺口 | 主干链路有跳步，或失败路径基本没讲，需要重新梳理 |
| < 70 | 不通过 | 需要重讲数据流，AI 可以给一个正确链路的提纲但不展开 |

**数据流讲解评分输出格式**：

```markdown
## 数据流讲解评分

总分：XX/100

| 维度 | 得分 | 评价 |
| --- | ---: | --- |
| 入口清晰 | /15 |  |
| 校验链路 | /15 |  |
| 业务编排 | /20 |  |
| 存储与外部调用 | /15 |  |
| 返回与副作用 | /15 |  |
| 失败路径 | /20 |  |

你的数据流讲解中做得好的：
1.

需要补充的：
1.

建议你讲的时候这样组织：「请求进来后，首先在入口层做了...，然后到业务层...」
```

## 4. S级代码质量评分（100 分）

用于 S级函数提交 Review 时。不同于普通的 code review——这个评分专门衡量「学习者手写的核心逻辑」。

| 维度 | 分值 | 评分重点 | 扣分信号 |
| --- | ---: | --- | --- |
| 正确性 | 25 | 逻辑是否满足设计文档中的要求，核心路径是否正确。 | 边界条件遗漏；正常路径能跑但异常路径 crash；状态转换不符合状态机定义 |
| 并发安全 | 20 | 共享数据是否有竞态，锁粒度是否合理，channel 使用是否正确。 | 共享 map 无锁；锁内做 IO；channel 关闭后写入；WaitGroup 计数错误 |
| 错误处理 | 15 | 错误是否被正确处理、传播、包装、记录，没有吞异常。 | `_ = err` 或 `log.Print(err)` 后继续执行；defer 中的错误被忽略；没有 wrap error context |
| 可读性 | 15 | 命名是否表达意图，分支是否清晰，函数是否单一职责。 | 函数超过 80 行无拆分；嵌套超过 3 层；magic number 无解释；变量名 `tmp`/`data`/`info` |
| 资源管理 | 10 | 连接、文件、锁、goroutine、channel 是否正确释放，有无泄漏。 | goroutine 无退出机制；channel 无关闭方；defer 顺序错误 |
| 测试覆盖 | 10 | 是否写了核心路径的单测，测试是否有边界和异常场景。 | 只测 happy path；没有并发测试；没有超时和取消场景测试 |
| 面试表达 | 5 | 提交时是否附了简洁的注释或说明，讲清为什么这样实现。 | 无任何说明直接提交代码 |

**分数解释**：

| 分数 | 结论 | 后续动作 |
| ---: | --- | --- |
| 90-100 | 优秀 | 代码质量和面试表达都到位，可以直接合并 |
| 80-89 | 合格 | 核心逻辑正确，有少量可读性或边界问题，修改后合并 |
| 70-79 | 基本正确 | 主体逻辑对，但并发安全或错误处理有遗漏，需要修复 |
| 60-69 | 有问题 | 存在正确性或并发安全缺陷，需要较大修改 |
| < 60 | 不通过 | 需要重新实现，AI 可以给设计方向引导但不给代码 |

**S级代码质量评分输出格式**：

```markdown
## S级代码质量评分 — `PickNextTask()`

总分：XX/100

| 维度 | 得分 | 评价 |
| --- | ---: | --- |
| 正确性 | /25 |  |
| 并发安全 | /20 |  |
| 错误处理 | /15 |  |
| 可读性 | /15 |  |
| 资源管理 | /10 |  |
| 测试覆盖 | /10 |  |
| 面试表达 | /5 |  |

必须修改：
1.

做得好的：
1.

验收结论：通过 / 不通过

面试口述建议：你可以这样讲你的实现——「我用了 xxx 来保证...，核心思路是...」
```

## 5. 阶段综合评分（100 分）

每阶段验收时的综合评分，由以下几个子项加权计算：

| 子项 | 权重 | 来源 |
| --- | ---: | --- |
| 设计评分 | 30% | 本阶段的设计 Review 评分（如有）或上一阶段的字段建模评分 |
| 代码质量评分 | 30% | 本阶段 S级代码质量评分的均值（如有多个 S级函数） |
| 数据流讲解 | 20% | 本阶段数据流讲解评分 |
| 文档完整度 | 10% | CHANGELOG.md 和 THOUGHT.md 是否完整、有实质性内容 |
| 面试表达 | 10% | 能否讲清本阶段的字段选型、分层职责、设计取舍和后续优化 |

**分数解释**：

| 分数 | 结论 |
| ---: | --- |
| 90-100 | 优秀。本阶段训练目标超额完成。 |
| 80-89 | 通过。可以进入下一阶段。 |
| 70-79 | 基本通过但需在下一阶段开始前补上本阶段遗漏项。 |
| 60-69 | 不通过。核心训练目标未达成，需要重新完成本阶段的关键任务。 |
| < 60 | 严重不足。需要重新执行本阶段。 |

阶段综合评分不是每阶段必须输出的——对短阶段或 B级为主的阶段可以简化。但 Stage 03（核心业务闭环）、Stage 06/07（高级特性）和最终验收阶段必须输出综合评分。

## 评分使用原则

1. **先给分数再解释**：让学习者第一时间看到量化结果，然后展开解释。
2. **每个维度都说清理由**：不要说「类型准确度 12/20」，要具体说「扣 8 分是因为金额用了 float——这是必须修改的错误」。
3. **进步要明确对比**：第二版评分时，必须对比第一版：「45 → 88，你真正理解了状态是核心」。
4. **低分不给答案，给方向**：分数低于 70 时，给引导问题和改进方向，不直接给正确方案。
5. **高分不纠缠小问题**：≥ 85 分后，微小的优化建议标注为「可选改进」，不阻塞通过。
6. **分数存入 THOUGHT.md**：每阶段的所有评分结果都要记录在 THOUGHT.md 中，形成完整的训练轨迹。面试时「你看我字段设计从 45 分迭代到 88 分」比「我设计了一个订单表」有说服力得多。
