# 聊天数据流与一致性

## 同步请求

```text
HTTP 请求
  -> 绑定并规范化 user_id/session_id/query
  -> 读取 Redis 最近窗口
  -> Agent 图：知识检索与对话分支
  -> 生成完整回答
  -> 写 Redis 短期记忆
  -> 尽力写 MySQL 长期历史
  -> 统一响应封装
```

规范化必须在进入 Agent 前完成：去除首尾空白，限制用户、会话和问题长度，并拒绝空问题。这样可以让同步和 SSE 共享同一套输入契约。

## SSE 请求

SSE 与同步接口共享 Agent 编排，但输出适配器不同：

1. 绑定、校验、读取记忆。
2. 启动带取消信号的流式生成。
3. 每个文本片段写成 `data: ...` 事件并及时 flush。
4. 客户端断开时停止生成和工具调用。
5. 流正常结束后，才把聚合后的 assistant 消息写入 Redis 和 MySQL。
6. 发送 `[DONE]`；发生错误则发送结构化错误事件并结束。

不要在每个 token 到达时写一次长期历史：这会放大数据库压力，也会保存半截回答。流式过程中的临时片段属于传输状态，完整回答才是持久化事实。

## 失败策略

- Redis 读取失败：记录 Trace-ID；按配置选择阻断、空上下文降级或只读 MySQL。
- MySQL 写入失败：回答仍可返回，但必须记录可重试的持久化失败。
- Agent/模型超时：返回稳定错误码，不暴露供应商原始错误。
- SSE 写入失败：取消下游 context，释放工具、连接和锁。

每一种降级都要在阶段验收中写成测试，而不是只写在注释里。
